# Viewer-context receipt: three affected paths and one control

**Result: in this synthetic localhost reproduction, each of the three affected
paths changes from two copies of the host utterance in one `viewer_context`
snapshot to one. SQLite stores one host utterance both before and after the fix.**

These are real WebSocket client receives from a temporary Pulsar server, not
mock `send()` calls. They are **not a production capture, an external-client
visit, or independent-party validation**. Every identity and message here is a
project-owned fixture. This does not establish conversation quality or whether a
listener understood a reply.

## Read the evidence

- [Before: received frames and SQLite rows](before.json), server revision
  [`8cb12f8`](https://github.com/pyosang82/atoa-stream/commit/8cb12f879ee154bd6f801eb3dd49b4780094fbfd).
- [After: received frames and SQLite rows](after.json), server revision
  [`85ed123`](https://github.com/pyosang82/atoa-stream/commit/85ed12362547d4db9b71ac0a06c66f5cd054e83f).
- [Counts and matching message IDs](counts.json), generated by
  [a separate Python reader](read_frames.py). The reader uses only the standard
  library and imports neither the server nor its SDK. It is still written by the
  project, so an independent review remains a separate step.
- [Capture program](capture.cjs) and [source/hash verification](provenance.json).

Each case contains the sent host command, the preceding audience line, received
`viewer_context`/`live_update` frames, and SQLite message rows. Registration frames,
session tokens, and broadcast keys are excluded. No participant conversation is
reproduced.

| Path | Host configuration/input | Copies in one context, before → after | Host live updates / stored rows before room end |
| --- | --- | --- | --- |
| `no-audio-expected` | Provider set, `audioExpected: false` | 2 → 1 | 1 / 1 |
| `browser-provider` | Provider `browser`, `audioExpected: true` | 2 → 1 | 1 / 1 |
| `no-provider` | Provider omitted, `audioExpected: true` | 2 → 1 | 1 / 1 |
| `pending-audio-control` | Other provider, `audioExpected: true`, no audio sent | 1 → 1 | 0 / 0 |

For the control, `broadcast_end` flushes the pending utterance: the client then
receives one `live_update` and SQLite has one host row. The context preview has no
message ID yet; the committed update has the same ID as the stored row. This
capture does not exercise arrival of actual audio bytes or a timeout flush.

`afterEnd.viewerFrames` is the **cumulative** capture, including `beforeEnd`.
Do not add their counts. Likewise, `viewer_context` is a snapshot for a reaction,
while `live_update` carries a committed delivery; the same utterance appearing
once in each is expected. The defect was two copies **inside a single snapshot**.
In the affected before-capture snapshots, one copy has the stored message ID and
the appended duplicate has no ID.

## Recount without running the server

From this directory, using Python 3:

```sh
python3 read_frames.py before.json after.json
```

The reader compares the unique sent host text against received messages and raw
SQLite rows. It checks all four named paths, the preceding audience line's order,
delivery/storage counts, IDs, and the pending preview. It exits nonzero if those
expectations differ. `counts.json` is its saved output. A separately written
reader can inspect the JSON directly without accepting these assertions.

## Reproduce the captures

Use two disposable checkouts at the full revisions linked above, with the
dependencies from each checkout's `v2/server/pnpm-lock.yaml` installed. The
published captures used Node 22.22.0. Run this capture program against each server
directory, providing its exact revision and a new output filename:

```sh
node capture.cjs /path/to/before/v2/server 8cb12f879ee154bd6f801eb3dd49b4780094fbfd fresh-before.json
node capture.cjs /path/to/after/v2/server 85ed12362547d4db9b71ac0a06c66f5cd054e83f fresh-after.json
python3 read_frames.py fresh-before.json fresh-after.json
```

The program starts the actual `src/index.js` on `127.0.0.1`, opens two WebSocket
clients per case, reads its disposable SQLite database, and deletes that temporary
database on exit. It does not use the production URL, import production identities,
send audio, or invoke a model. IDs and timestamps will vary. The supplied revision
is metadata; verify the captured protocol/bootstrap hashes against that revision
as shown in `provenance.json`.

The narrow claim supported here is that the repaired server delivered one copy
per reaction-context snapshot over this local socket path. A production receiver
capture and an independently authored review are still unconfirmed.
